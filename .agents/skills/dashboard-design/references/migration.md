# 現在のCSS構造（移行途中）

2026-08-08時点の構造を記録する。維持すべき設計ではなく、残りを片付けるための地図である。すべて解消したらこのファイルを削除する。

## 3層構成

制御画面のCSSは3つの文字列を連結して配信している（`web/pages.ts` の `dashboardStyleResponse`）。

| 層 | 場所 | 役割 |
|---|---|---|
| トークン | `web/design-tokens.ts` の `DESIGN_TOKEN_STYLE` | 値の正本。light／darkのマップから3つのCSSブロックを生成する |
| 基底 | `web/pages.ts` の `DASHBOARD_STYLE` | 全面のレイアウト、寸法、レスポンシブ |
| 骨格・意味 | `web/dashboard-design.ts` の `DASHBOARD_DESIGN_STYLE` | 面の型ごとの骨格、操作・状態・種別の表現 |

トークン層は `:root` で全面へ届く。開示面と作業面は同じ配色になっている。

## 触るときに壊れる場所

**幾何を2層に書かない。** 基底層のメディアクエリを、骨格層の無条件の指定が打ち消す事故が2件起きた（作業面の広い画面での幅、狭い画面での `.section-head` の寄せ）。条件付きの指定を上書きするときは、同じ条件を骨格層側にも書く。

**上書きは具体クラス名への再指定で成立している。** 基底側のクラスを消したり改名すると、骨格層が静かに効かなくなる。片方だけを変更しない。

**プレビューはBunで生成し、本番はesbuildでビルドする。** `String.raw` 内の非ASCII文字の扱いが違う。詳細は [verification.md](verification.md)。

## 調べた結果、やらないと決めたこと

**`data-state` を5属性へ分割しない。** 操作は同じ `button` が別の意味を持つため `data-op` の宣言が要ったが、状態は表示ごとに別のクラスを持ち、クラスが系統を特定している（`.save-state`＝保存、`.voice-status`＝生成、`.anchor-state`＝鮮度、`.journey-step`＝進行、`.preflight-item`＝判定）。3系統が重なる `.project-status` だけ `data-kind` で切り分け済みである。分割してもマークアップ、ブラウザ側5箇所、テスト9箇所を触るだけで、読みやすさも保守性も変わらない。

残る難点は値の語彙で、「問題なし・到達済み」を `ok`、`complete`、`saved`、`ready`、`idle` が別々に表している。揃える価値はあるが、見た目に出ない変更のためにブラウザ側とテストを触ることになる。状態表示のマークアップへ別の理由で手を入れるときに、ついでに揃える。

## 残っている作業

1. 基底層と骨格層の統合。骨格層が基底層のクラスへ再指定する構造は残っている。約1,000行の機械的な移動になり、利用者に見える改善が無い一方で回帰の危険がある。層をまたぐ打ち消しは下の監査で検出できるため、統合そのものは急がない。
2. `image-size` の除外解除。`.github/workflows/deploy-mcp.yml` の `--ignore` は、上流に修正版が出るか旧発表アプリを `apps/presentation` へ移した時点で外す。

## 層をまたぐ打ち消しの監査

基底層のメディアクエリを骨格層の無条件指定が打ち消す事故が3件起きた（作業面の幅、`.section-head` の寄せ、これらは修正済み）。同じ型を再発させないため、幅を変えて計算後スタイルを実測する。

```bash
agent-browser set viewport 390 844
agent-browser eval "getComputedStyle(document.querySelector('SELECTOR')).PROPERTY"
agent-browser set viewport 1280 720
```

2026-08-09時点で残存ハザードは無い。骨格層で条件付きの指定を上書きするときは、同じ条件を骨格層側にも書く。

各段階で `bun run preview:dashboard` を実行し、全面の実表示を確認してから次へ進む。
