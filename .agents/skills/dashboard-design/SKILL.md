# 制御画面デザイン

見た目を直す前に、その画面が何をする面で、その操作が何をする操作かを決める。制御画面のデザインは意匠ではなく、役割分解の写像として作る。

## 判断の枠組み

`docs/dashboard-roles.md` が制御画面の役割分解の正本で、3つの表を持つ。

- **面の型**（6種）— 開示・選択・現在地・作業・指摘・監視
- **操作の意味**（6種）— 移動・確認・編集・依頼・確定・破棄
- **状態の系統**（5系統）— 進行・鮮度・保存・生成・判定

`docs/dashboard-design-system.md` が、この3つの表から導いた具体の決定（配色、骨格、表現）を持つ。

作業前に両方を読む。分解を読まずに決定だけを読むと、当てはまらない要素が出たときに個別の見た目を足す方向へ倒れる。

## モードを選ぶ

| 依頼の性質 | モード |
|---|---|
| 配色体系、骨格、操作表現、状態表現そのものを決める・変える | `define` |
| 決まっている表現で画面を作る・直す | `apply` |
| 既存画面が分解と一致しているかを調べる | `audit` |

依頼が「デザインを見直したい」のように曖昧なら、まず `audit` で差分を出し、何を `define` し直すかをユーザーと決める。いきなり画面を書き換えない。

## define — デザインシステムを決める

1. 対象が面の型・操作の意味・状態の系統のどれに属する決定かを言う。
2. 分解の表に無い要素が必要なら、表を先に更新する。表を飛ばして例外を作らない。
3. 決定は必ず「どの分解のどの行に対応するか」とセットで書く。対応の無い決定は残さない。
4. トークンの正本は実装側のCSS変数定義に置き、`docs/dashboard-design-system.md` には決定と理由を書く。同じ値を二重に持たない。
5. 変更前後を実表示で比較する。手順は [references/verification.md](references/verification.md)。
6. `docs/dashboard-design-system.md` を同じ変更に含める。

配色を決めるときは、5つの状態系統それぞれに、色・形・文言の3点セットを与える。色だけで区別する案は採らない。

操作表現を決めるときは、6種の意味それぞれが1280×720で隣り合ったときに区別できるかを確認する。強調を一つに絞ることと、残りを無差別に平坦化することは違う。

## apply — 決まった表現で作る

1. 触る画面がどの面の型かを決める。型が同じ既存画面の骨格を使い、ページ固有の骨格を新設しない。
2. 置く操作を6種の意味へ、表示する状態を5系統へ割り当てる。割り当てられないものが出たら `define` へ戻る。
3. 実装する。生の色値を個別クラスへ足さず、トークンを使う。
4. 実表示で確認する。[references/verification.md](references/verification.md)。

HTML構造を変えるときは、`web/assets.ts` のブラウザ側スクリプトが同じクラス名や `data-` 属性を参照していないかを先に確認する。制御画面の見た目とふるまいは別ファイルに分かれているが、セレクタで結合している。

## audit — 分解との差を出す

1. `bun run preview:dashboard` で全面を生成する。
2. 面ごとに、型・操作の意味・状態の系統を実際のHTMLから数える。印象で判断しない。

```bash
rg -o 'class="(button[^"]*|ghost[^"]*|[a-z-]*danger[^"]*)"' apps/mcp-server/src/web/pages.ts | sort | uniq -c | sort -rn
rg -o 'data-(state|level|complete)="[^"$]*"' apps/mcp-server/src/web/pages.ts | sort | uniq -c | sort -rn
```

3. 差分を `docs/dashboard-roles.md` の「現状との差」の形で述べる。件数と根拠のファイルを付ける。
4. 直す順をユーザーへ提案する。勝手に直し始めない。

## 守ること

- 分解の表に無い見た目を足さない。必要なら表を更新してから足す。
- 状態を色だけで伝えない。文言を必ず伴わせる。
- 待つべき状態（生成中）と直すべき状態（要修正）を同じ表現にしない。
- 確定（公開・復元）と破棄（削除）を、可逆な操作と隣接させない。
- ライトとダークで情報構造と操作階層を変えない。
- 利用者入力から任意のCSSやHTMLを受け取る経路を作らない。検証済みの値とCSS変数だけを使う。
- 影はモーダル、ポップオーバー、フロート操作だけに使う。

## 現在の実装

制御画面のCSSは移行途中で、基底層と上書き層の2枚構成になっている。触る前に [references/migration.md](references/migration.md) を読む。移行が終わったらこの参照ファイルを削除する。

## 配信版の更新

CSSまたは `web/assets.ts` を変更したら `src/web/assets.ts` の `DASHBOARD_ASSET_VERSION` を上げる。この値はテスト側の期待値と対になっているため、上げたときは揃える。

```bash
rg -n "dashboard\.(css|js)\?v=" apps/mcp-server/test
```

見た目が変わらない内部整理だけなら上げない。

## 完了条件

- `bun run test:mcp` が成功する。
- ライトとダークの両方を実表示で確認した。
- 変更したページだけでなく、同じ型の他の面と、同じクラスを共有する面の表示を確認した。
- 加えた変更が、分解のどの行に対応するかを説明できる。
- 分解または決定を変えた場合は `docs/dashboard-roles.md` または `docs/dashboard-design-system.md` を同じ変更に含めた。
