# ADR 0010: スライドレビューを独立データと引用アンカーで管理する

## 状態

採用（2026-07-30）

## 決定

- 一枚編集inspectorへコメントUIを追加せず、filmstrip、実renderer、平坦な保存テキスト、コメント欄を持つ専用レビュー画面を用意する。
- コメントは研究documentへ含めず、D1の`slide_review_comments`へ所有者、研究、スライド、作成時versionとともに保存する。
- コメント対象はスライド全体、画面テキスト、音声原稿に分け、flow、canvas、scene、narrationから安定した`target_key`を生成する。
- 範囲はUTF-16 offsetと選択文を保存し、作成時はサーバー上の現在本文との完全一致を要求する。後の表示では位置一致、一意な再発見、要再指定を区別する。
- 未解決コメントは標準MCPのページ化resourceで読む。書き込みtoolは追加せず、既存の小粒度編集toolを使う。
- Web UIが生成するのは実行可能scriptではなく、選択した最大20件、現在version、resource URI、編集制約を含むAI修正依頼文とする。
- AIはコメント状態を変更しない。利用者が実表示を確認した後、Web UIで解決または再開する。
- コメント追加・状態変更・削除は研究versionを増やさず、固定previewの現在性にも影響させない。

## 理由

編集画面はすでに内容、デザイン、読み上げ、構造、品質確認を持ち、さらにレビューを重ねると「作る」と「確かめる」の操作が混ざる。専用画面なら実表示と全保存テキストを同時に見ながら指摘でき、第三者が編集権限を持たない将来のレビューにも同じデータモデルを使える。

offsetだけでは文章の前方編集で誤った位置を指し、選択文だけでは同じ語が複数ある場合に特定できない。offset、選択文、前後文脈を併用し、一意に再発見できない場合は止めることで、AIが別の箇所を黙って修正する事故を避ける。

## 見送った案

- コメントを研究JSONへ含める案は、指摘追加だけで発表versionと固定previewを古くし、研究documentの512 KiB上限も消費するため採用しない。
- DOM nodeや生成HTMLへ直接アンカーする案は、renderer versionやレイアウト変更で壊れ、MCPの編集対象とも一致しないため採用しない。
- 任意の修正JavaScriptやshell scriptを生成する案は、利用者入力をコード実行へ接続し、所有者・version・schema検証を迂回するため採用しない。
- コメントを一括更新する大型MCP toolは、既存の8 KiB未満のinput schemaと小粒度編集契約に反するため採用しない。

## 制限

- 初期段階ではコメントの共同編集、メンション、外部通知を扱わない。
- 一つのコメント範囲は一つの保存テキスト項目内、最大2,000文字とする。
- 一研究200件、AI修正依頼文一回20件を上限とする。

## 検証

- flow、canvas、scene、音声原稿の平坦化と安定keyをunit testで固定する。
- 完全一致、一意な位置移動、重複または削除によるstaleを自動検証する。
- Web E2Eでログイン、CSRF、作成、表示、依頼文生成、解決、削除を通す。
- MCP contract testでindexとpage resourceを列挙・読取できることを確認する。
