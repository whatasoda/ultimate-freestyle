# 制御画面の役割分解

この文書は、制御画面を「何をする道具か」から分解する。配色や寸法は決めない。それらは `docs/dashboard-design-system.md` が、この分解を入力として定める。現在の実装がこの分解と一致していない箇所は「現状との差」に挙げる。

対象は `apps/mcp-server/src/web/` が生成する画面に限る。発表rendererは研究ごとのデザインを持つ別の系であり、この分解の外にある。

## 1. 制御画面が引き受けている仕事

研究の制作はAIクライアントと制御画面で分担する。分担は `docs/設計.md` が正本で、要点は次の通り。

| AIが引き受ける | 制御画面が引き受ける |
|---|---|
| テーマを探す、問い・方法・記録を整理する | 本人であることを示す |
| 発表の流れとスライドを構成する | 画像を追加する |
| 対象を読んで小さな単位で修正する | 実際の表示を見る |
| | 文言・見た目・音声を仕上げる |
| | 固定プレビューを確認し、公開を決める |

制御画面の中心は**見て決めること**であり、ゼロから作ることではない。編集機能は持つが、それは「見た結果を直す」ための仕上げの粒度に閉じる。大きな構成変更はAIへ渡す。

この性格から、制御画面のデザインには2つの要求が生まれる。

- **現在の状態が、操作より先に読めること。** どの面でも「今どうなっているか」が最初に目へ入り、「次に何をするか」がその直後に来る。
- **不可逆な決定が、可逆な操作から明確に隔たっていること。** 公開と削除は取り消せない。仕上げの編集は何度でもやり直せる。この差が見た目に出る。

## 2. 対象の階層

制御画面が扱う対象は5階層で、面はこのどれかに責任を持つ。

```text
研究の集合 ─ 研究 ─ 発表 ─ スライド ─ パーツ / 読み上げ区間
```

一つの面が2階層以上を同じ強さで扱わない。上位階層を示すのは現在地の表示であって、操作対象ではない。

## 3. 面の型

面は6種類に分かれる。同じ型の面は同じ骨格を持ち、違う型の面は違う骨格を持つ。ページごとに骨格を作らない。

| 型 | 責任 | 対象階層 | `data-surface` | 現在の実装 |
|---|---|---|---|---|
| 開示面 | 読ませる。ログイン前に判断材料を渡す | — | `disclosure` | `/`、`/guide`、`/data` |
| 選択面 | 集合を見比べて、次に手を入れる一つを選ぶ | 研究の集合 | `select` | `/dashboard` |
| 現在地面 | 一つの対象の全体像と、公開までの残りを示す | 研究 | `overview` | `/dashboard/projects/{id}` |
| 作業面 | 対象を見ながら細部を仕上げる | スライド | `workspace` | `.../slides/{slideId}` |
| 指摘面 | 保存済みの内容を読み、位置を指して記録する | スライド | `review` | `.../review` |
| 監視面 | 集合の処理状態を追い、揃うまで待つ | 読み上げ区間 | `monitor` | `.../voice` |

面は `<main data-surface="...">` で自分の型を宣言する。宣言のない面を作らない。

型ごとの骨格は次の性質で決まる。

- **開示面** — 縦一列。操作は最後に一つだけ。読み終わるまで判断を求めない。
- **選択面** — 一件一行。比較すべき軸（進行段階、鮮度、次の一歩）が列として揃う。一件をカード化しない。
- **現在地面** — 冒頭に到達状況、その後に領域別の詳細、末尾に確定操作。詳細は畳んでよいが、状況は畳まない。
- **作業面** — 対象一覧・実表示・編集の3領域を同時に見せる。編集で変えた結果が実表示へ即座に返る。
- **指摘面** — 中央に連続した流れ。読む対象と書く場所が同じ列にある。独立スクロール領域を作らない。
- **監視面** — 全体の到達数が先、個別の状態が後。処理中でも画面を離れられることを示す。

作業面と指摘面は同じスライドを扱うが、目的が違う。作業面は「直す」、指摘面は「記録する」。両者を一つの面へ統合しない。

## 4. 操作の意味

操作は結果の性質で7種類に分かれる。見た目の強さではなく、この意味で分類する。

| 意味 | 結果 | 取り消し | 例 |
|---|---|---|---|
| 移動 | 別の対象・別の面へ行く | 戻れる | 研究を開く、スライドを選ぶ、節へ飛ぶ、外部の手引きを開く |
| 確認 | 何も変わらない | 不要 | 実表示を見る、試聴する、絞り込む、畳む／開く |
| 編集 | 対象の値が変わり、版が上がる | やり直せる | 文言、組版、配置、調声値、部品の追加・複製 |
| 実行 | 処理が始まる・止まる | 繰り返せる | 音声を生成する、一括チェックを始める、中断する |
| 依頼 | AIへ仕事を渡す。結果はこのアプリの外で起きる | 不要 | 相談文・監査文をコピーする |
| 確定 | 外向きの状態が変わる | 別操作で戻す | 固定プレビュー作成、公開、版の復元 |
| 破棄 | 対象が消える | 戻せない | スライド削除、研究削除、アカウント削除 |

**実行を編集と分けるのは、待ち時間が生まれるからである。** 編集は押した瞬間に終わるが、実行は状態の「生成」系統へ結果が出るまで時間がかかる。利用者は待つか、画面を離れるかを決める必要がある。

**編集には2つの形がある。** 作業面は自動保存で、保存ボタンを持たず保存状態だけを表示する。現在地面は領域ごとの明示保存で、領域の末尾に保存操作を1つ置く。どちらも「値が変わり版が上がる」点で同じ意味だが、形が違う。片方の形をもう片方へ持ち込まない。

デザインが満たすべき条件は4つ。

1. **確定と破棄は、他の5種から視覚的に隔たる。** 隣接して置かない。押す前に対象と結果が読める。
2. **移動・確認・編集・実行・依頼は互いに区別できる。** 同じ見た目にしない。特に「依頼」はAIへ仕事を渡すため、内部操作と混ぜない。
3. **意味と強調は別の次元で表す。** 意味は面の有無と記号で示し、強調は塗りで示す。塗りを特定の意味へ固定しない。領域で最も進行に寄与する一つだけを塗る。
4. **一つの領域で塗るのは一つだけ。** 残りを無差別に平坦化せず、意味ごとの差を残す。

条件1と4は既存のデザインシステムが持っていたが、2と3は無かった。

## 5. 状態の意味

状態は5系統ある。系統が違えば、利用者が取るべき行動も違う。

| 系統 | 問い | 値の例 | 利用者が取る行動 |
|---|---|---|---|
| 進行 | どこまで進んだか | 未着手 / 作業中 / 完了 | 次の段階へ進む |
| 鮮度 | 表示中のものは現在版か | 一致 / 内容が古い / renderer が古い | 作り直す |
| 保存 | 入力は保存されたか | 保存済み / 未保存 / 保存中 | 待つ、または離れない |
| 生成 | 処理は終わったか | 未生成 / 実行中 / 完了 / 失敗 | 待つ、再実行する |
| 判定 | 内容に問題があるか | 問題なし / 注意 / 推奨 / 要修正 | 直す |

デザインが満たすべき条件は3つ。

1. **系統ごとに表現を分ける。** 「完了」と「保存済み」と「生成済み」を同じ表現にしない。取るべき行動が違う。
2. **色だけで伝えない。** 各状態は文言を伴う。色は文言を補強するだけで、単独の情報源にしない。
3. **待つべき状態と、直すべき状態を混ぜない。** 生成中と要修正は、利用者の行動が正反対である。

## 6. 対象の種別

同じ面に、同じ形で並びながら、性質の違うものがある。これは状態でも操作でもない。

| 現れる場所 | 種の数 | 混在して走査するか |
|---|---:|---|
| レビュー面の対象 | 2（画面テキスト／音声原稿） | する |
| スライドの役割 | 6（表紙／章扉／本文／比較／結果／結び） | する |
| スライドの構成モード | 3（flow／canvas／scene） | する |
| 研究ログの種類 | 5（観察／実験／決定／出典／メモ） | する |
| AIクライアント | 3（Claude／Codex／ChatGPT） | しない。並べて選ぶ |

**種別は色相を持たない。**

種別は最大6種あり、面ごとに数が違う。色相を割り当てれば6色が要り、状態の表現と必ず衝突する。実際、役割・構成モード・ログ種別はラベルだけで機能してきた一方、色を与えた2つのうちAIクライアントは、Claudeが要対応、Codexが達成、ChatGPTが進行中の色を占め、カードが状態表示に見えていた。

表現は3段階で、必要な分だけ使う。

1. **ラベル** — 常に必須。種別名を文字で書く。
2. **位置** — 同じ種別を隣接させる、または列を分ける。
3. **面の質** — 走査しながら区別する必要がある場合だけ。面の有無、罫線、字体で差をつける。色相は使わない。

3段目まで要るのは、今のところレビュー面だけである。画面テキストは面を持ち、音声原稿は面を沈めて左罫線を持つ。表示されるものは枠の中にあり、読み上げられるものは流れる、という差に対応させる。

## 7. 現状との差

2026-08-08時点。解消したものは `docs/dashboard-design-system.md` の「実装の状態」に残す。

**状態の語彙が一つの属性へ混在している。** `data-state` は依然として19種類の値を取り、進行・保存・鮮度・生成・判定の5系統が同居する。表現の割り当ては系統ごとに分けたが、属性名からは系統が読めない。系統が衝突した箇所には `data-kind` を足して切り分けているため、属性の設計としては一貫していない。

## 8. この分解の使い方

デザインシステムは、この分解の4つの表を入力として次を定める。

- 面の型 → 骨格（領域の分割、幅、スクロールの単位、余白の段階）
- 操作の意味 → ボタンとリンクの表現（塗り、枠、文字のみ、配置と間隔）
- 状態の系統 → 状態表示の表現（色、形、文言の型）
- 対象の種別 → ラベル、位置、面の質（色相を除く）

色を使えるのは状態だけである。操作は形と配置、種別はラベルと面の質で分ける。この配分により、意味色は状態の表現数だけで足りる。

画面を新しく作るときは、まず面の型を決め、次に操作を6種類へ、状態を5系統へ、並ぶものを種別へ割り当てる。当てはまらないものが出たら、個別の見た目を足す前にこの文書を見直す。
