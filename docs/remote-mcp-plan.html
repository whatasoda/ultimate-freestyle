DECISION

利用者はMCP対応AIクライアントを用意する

  • 専用チャット画面は作らない
  • 初期の対応・検証対象はCodexとChatGPTを優先する

01 / Design principles

責務を小さく、境界を明確にする

MCPサーバーは会話AIそのものではなく、研究データと制作機能を安全に提供する道具箱として設計する。

01

OpenAIクライアントを先行

CodexとChatGPTを第一の受け入れ対象にする。Claudeなども標準MCPの範囲で維持するが、初期開発の判断はOpenAIクライアントを優先する。

02

データは構造化

研究、スライド、読み上げ、BIIM補足を検証可能なJSONとして保存。HTMLやJavaScriptをそのまま実行しない。

03

公開だけ強く守る

下書き編集と公開を分離。公開・音声生成・削除など影響の大きな処理は再認可、明示確認、監査の対象にする。

02 / System architecture

ひとつのWorkerを入口にする

MCP OAuth、Twitch OAuth、権限判定、ツール呼び出しを同じ信頼境界に置く。 永続データと生成物だけを用途別サービスへ逃がす。

03 / Authentication & eligibility

二段のOAuthをWorkerでつなぐ

MCPクライアントが受け取るのはWorker発行のMCPトークン。TwitchトークンはWorkerの外へ出さない。

  1. MCPクライアントが接続 /mcpが401を返し、OAuth metadataを案内する。
  2. Workerの認可画面を開始 MCP OAuth 2.1のcode challengeと要求scopeを検証する。送信時はボタンを即時に無効化し、処理中表示で二重送信を防ぐ。
  3. Twitchへリダイレクト 追加クリックを要求せず、自動遷移と失敗時だけ使うリンクでAuthorization Code Grantの同意画面へ進む。
  4. 利用資格を照会 対象配信者のIDでフォロー日時と現在のサブスクを確認する。
  5. MCP用トークンを発行 資格と同意scopeを紐づけ、日英併記の完了案内を表示してからMCPクライアントへ返す。
  6. 各toolで再度認可 所有者・scope・資格期限をhandler側でも必ず確認する。

Codexは認可コードを受け取る一時的なloopback callbackとして http://127.0.0.1:<random-port>/callback/...を使う。 この最終ページはCodex側が配信するためWorkerから装飾できない。Workerは直前に日英併記の案内を表示し、自動で接続元へ戻す。

Twitchに要求するscope

user:read:follows
本人が対象チャンネルをいつからフォローしているか確認する。

user:read:subscriptions
本人が対象チャンネルを現在サブスクしているか確認する。

MCPで分けるscope

research:read 閲覧・評価

research:write 作成・編集

research:publish 公開・音声生成

現在サブスク中 継続月数はMVPの条件にしない
OR
フォロー経過日数 ≥ 設定値 followed_atから計算
AND
denylist対象外 運営上の停止・不正利用へ対応

対象配信者はログイン名ではなく変更されないTwitch broadcaster IDで設定する。 フォロー解除後に再フォローした場合は新しいfollowed_atを基準にする。

AIが自律検証できる契約

すべてのtoolはJSON Schema、安定したerror code、request_id、 変更後のversionを返す。初期化時のinstructions先頭には、推奨手順、 destructive操作、quota、再試行条件を短く完結して記載する。

ブラウザに依存しない検証

Twitch API adapterのfixture、資格判定のtable test、MCP protocol contract test、 previewのsnapshot、公開URLのsmoke testを用意する。実OAuthログインだけを人による最終確認に残す。

06 / VOICEVOX on Containers

音声はCloudflare内の短命ジョブで作る

Workers上ではなくCloudflare Containersで公式VOICEVOX ENGINEのCPU版を動かす。 MCPの応答を待たせず、差分segmentをまとめた非同期ジョブとして処理する。

request_voice_generation 資格、project所有権、月間quota、原稿versionを確認
get_voice_job queued / running / completed / failedを取得
→
D1 + Queue jobを冪等登録し、Workerから即座にjob IDを返す
VOICEVOX Container standard-2を初期値に、変更segmentを一括生成
ffmpeg 一時WAVをモノラルMP3へ変換し、変換後に削除
→
Public R2 project version配下へMP3を保存
Fingerprint cache 原稿・話者・設定・ENGINE version一致時は再利用
Scale to zero 一括生成後は短いsleepAfterでContainerを停止

初期インスタンス

standard-2：1 vCPU、6GiBメモリ、12GBディスク。約1.85GBの公式CPUイメージと一時音声を扱う余裕を持たせる。

デプロイ方針

latestを実行時に直接参照せず、ENGINE versionまたはdigestを固定したDockerfileをCloudflare管理レジストリへ配置する。

切替条件

10分以内に20分発表相当の変更分を生成できない、またはメモリが収まらない場合はstandard-3を試す。それでも不十分ならCloud Run Jobsを代替候補にする。

事前ベンチマーク確認する値初期判定
Container起動起動から/speakers応答までタイムアウトと再試行設計を決める
文章長100・500・2,000文字の合成時間segment上限と分割規則を決める
発表一式20分相当の変更segment一括生成10分以内を目標
資源ピークメモリ、展開後イメージ、一時WAVstandard-2内に収まるか確認
再実行同じfingerprint、途中失敗、二重要求再生成せず安全に収束

ContainerへTwitch tokenやMCP tokenを渡さない。VOICEVOXの内部HTTPポートは公開せず、専用R2 bucketへの必要最小限の経路だけを持たせる。 公開画面には「VOICEVOX:キャラクター名」のクレジットと、音声ライブラリ・キャラクター固有規約への導線を表示する。

07 / Security boundary

AIから来る値を信用しない

MCPクライアントが正規でも、モデルの誤操作、プロンプトインジェクション、利用者入力の悪用は起こり得る。

認証・認可

  • OAuth stateをSecure・HttpOnly・SameSite cookieへ結びつけ、使用後に削除
  • MCP consent画面に要求scopeと実行可能な操作を表示
  • Twitch access/refresh tokenは暗号化して保存し、ブラウザ・MCP・ログへ出さない
  • 起動時・定期的にTwitch tokenを検証し、失効時はMCPセッションを停止
  • 公開など高コスト操作の直前に利用資格を再確認

入力・生成物

  • toolごとに厳格なJSON Schema、文字数、配列件数、容量上限を設定
  • Markdownをサニタイズし、任意HTML・JS・CSS・SVG・ZIPはMVPで拒否
  • 画像は拡張子でなく実MIME、サイズ、ピクセル数を検査
  • R2へはWorker経由で限定keyにだけ保存し、公開bucketへの直接writeを許さない
  • HTML生成はサーバー所有のrendererだけで行う

AI・MCP固有

  • アップロード文書内の命令をシステム指示として扱わない
  • 利用者に許可されないtoolは条件付き登録でモデルから隠す
  • 公開・削除・音声生成には確認用previewと明示承認を要求
  • 汎用shell、任意URL fetch、秘密情報の読取toolを公開しない
  • VOICEVOX Containerには原稿と生成設定だけを渡し、Twitch・MCPの秘密情報を渡さない
  • エラー本文へ内部パス、SQL、token、stack traceを含めない

運用・費用

  • Twitch user、IP、tool、日単位のrate limitとquotaを設定
  • 音声生成は月間回数、総文字数、同時job数を利用者ごとに制限
  • 同じ要求を重複実行しないidempotency keyを採用
  • 監査ログに誰が・いつ・何をしたかを残す
  • 管理画面はCloudflare Access等で別に保護
  • 緊急停止、denylist、全token失効の手順を用意
HIGH
任意コード実行

MVPでは実装しない。将来必要になった場合だけ、ユーザー／ジョブごとに隔離したSandboxを追加する。

HIGH
公開操作の誤実行

下書き更新とは別scope・別toolにし、preview hashへの承認を要求して公開内容を固定する。

MEDIUM
資格キャッシュ中のフォロー解除・サブスク終了

通常toolは短期キャッシュ、高コスト・公開toolはTwitchへ再照会する。猶予期間の有無は運用規約で決める。

08 / Monthly cost model

30 MAUなら月5〜10ドルを基準にする

制作者30 MAU、閲覧200 DAU、1人あたり月4回の音声生成を初期モデルとする。 閲覧はCloudflare配信で完結し、GitHub PagesとGitHub Actionsは構成に含めない。

$5

基盤

Workers Paidの最低料金。約14万Worker request、D1、KV、Queue、10GB以内のR2は初期想定では包含枠内。

$0

静的配信・egress

Workers Static Assetsへのrequestは無料。R2は10GBまでと月1,000万Class B操作が無料で、Internet egressも無料。

+$5

音声生成の上振れ枠

月120jobをCPUで処理し、1jobが20分近くかかった場合まで見た概算余裕。差分生成により通常は小さくなる。

月120回のVOICEVOX生成Container稼働基盤込み概算判断
平均3分／job月6時間約$5.10CPU包含枠内。メモリ超過のみ小額
平均10分／job月20時間約$6.90初期運用の現実的な上限候補
平均20分／job月40時間約$9.50性能改善またはstandard-3比較を行う

この金額は実測前の計画値。D1にjobごとのContainer実行時間、生成文字数、cache hit、出力byte数を記録し、 運用開始後に「1,000文字あたりの原価」と「1公開あたりの原価」へ更新する。

09 / Implementation roadmap

認証を先に証明し、制作機能を後から載せる

各段階を単独で検証できるようにし、資格判定や公開処理を一度に作り込まない。
